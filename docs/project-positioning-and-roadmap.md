# Mojobox 项目定位与发展路线

> 本文记录 Mojobox 的长期项目定位、职责边界和开发顺序。
> 它是方向性文档。当前皮肤包接纳工作已同步扩展收录 Schema、目录构建和静态网站；具体字段和命令仍以 [`docs/intake.md`](intake.md) 为准。

> 2026-10-10 决策更新：用户转述下游认可前两轮草稿且不再要求逐批反馈，当前优先级转为
> 中量插件收录与稳定来源接口。本地已形成 26 条插件目录和[插件来源接口 v1](plugin-source-api-v1.md)；
> 发布、下游新入口适配与宿主运行验证是独立步骤，不能由草稿认可自动推导完成。

## 1. 项目定位

Mojobox 是 DSH 生态中的插件与整合包中介平台，负责把分散在 npm、GitHub Release、插件仓库和开发者整合包中的产物整理成可追溯、可检查、可供下游使用的目录和归档。

Mojobox 的核心价值有四点：

1. **收纳**：集中记录插件、功能整合包和皮肤整合包。
2. **规整**：统一记录身份、版本、来源、作者、许可证、依赖和冲突信息。
3. **检验**：检查清单、归档布局、来源声明和文件摘要，区分静态事实与运行证据。
4. **供给**：向网站用户、宿主市场、皮肤加载器和其他下游工具提供稳定的目录数据、下载地址和来源摘要。

Mojobox 不以开发插件或皮肤为目标，也不以替代宿主、加载器或包管理器为目标。上游作者维护实际内容，下游工具负责消费和运行，Mojobox 维护两者之间可靠的来源层。

推荐对外表述为：

> Mojobox 是 DSH 生态的插件与整合包收录、验证、归档和分发目录，为宿主、皮肤加载器及其他下游工具提供稳定、可追溯的来源数据和下载支持。

## 2. 上下游责任关系

Mojobox 位于上游开发者和下游运行工具之间：

```text
插件作者 / 皮肤作者 / 整合包作者
              │
              │ 产物、版本、来源、许可证、兼容声明
              ▼
          Mojobox
  收录 · 规整 · 静态检查 · 归档 · 分发
              │
              │ 目录、下载地址、摘要、证据、限制
              ▼
宿主市场 / 皮肤加载器 / 第三方安装器 / 开发者工具
```

| 参与者 | 主要责任 | 不应由其承担的责任 |
| --- | --- | --- |
| 插件作者 | 代码、入口、依赖、版本、发布产物和更新 | Mojobox 的目录维护 |
| 皮肤作者 | 皮肤实现、素材授权、皮肤包组合和冲突声明 | Mojobox 的加载器实现 |
| 整合包作者 | 插件组合、整合包清单、兼容范围和升级说明 | 宿主的安装事务 |
| 皮肤加载器作者 | 发现、加载、切换、禁用和运行时兼容 | Mojobox 的来源审计 |
| 宿主作者 | 插件安装、Profile、启动、回滚和运行环境 | Mojobox 的公开目录维护 |
| Mojobox | 收录、规整、检查、保存、展示和提供下载 | 插件开发、皮肤渲染、完整安装器 |

这里的“中介”不是替上游重新生产内容，而是保存事实和来源关系。Mojobox 可以托管开发者交付的原始归档，但不能把未经授权的多个项目重新组合成一个声称由上游维护的产品。

## 3. 五项发展目标

### 3.1 完善功能整合包收录，并提供有限安装支持

功能整合包是 Mojobox 的第一条主线。目标是让开发者提交一个薄 Feature Pack，Mojobox 能够：

- 保存开发者提供的原始 `.dshpack`；
- 检查根 `pack.json`、插件引用、归档路径和摘要；
- 展示名称、版本、来源、作者、许可证和内核要求；
- 提供原始归档、清单和检查报告下载；
- 为已有宿主市场或官方 Feature Pack CLI 提供可消费的来源；
- 在宿主已有安装能力的前提下，提供有限的安装调用支持。

“有限安装支持”有明确含义：Mojobox 可以提供宿主能够读取的索引和归档，也可以通过薄 Host Adapter 调用宿主已有的检查与安装接口；Mojobox 不自己实现依赖解析、Profile 管理、快照、回滚或插件运行。

浏览器网站的下载不等于桌面端安装。用户仍然需要安装相应宿主能力，宿主是否能安装和运行以宿主实测为准。

### 3.2 拓展皮肤包收录，向来源中介靠拢

皮肤包是第二条主线。Mojobox 可以收录：

- 单个皮肤插件；
- 多个皮肤插件组成的薄整合包；
- 皮肤管理器、皮肤加载器或相关依赖的来源记录；
- 皮肤预览、兼容声明、冲突说明和许可证信息。

皮肤方向采取“收录、检查、归档、供给来源”的策略。Mojobox 不开发桌面端皮肤加载器，不负责皮肤发现、注入、切换、渲染、素材管理或运行时回滚。

皮肤包可以被下载和被下游读取，但不能仅因为已经进入目录，就显示为“已安装”“已加载”或“兼容所有宿主”。皮肤运行状态必须由对应加载器或宿主提供证据。

### 3.3 收录真实可用的包，逐步确定规范和边界

规范从真实案例中提炼，而不是先为所有可能的插件类型设计完整协议。每个新类型先经过小规模试点，确认以下事实：

- 是否存在明确的根插件或整合包入口；
- 是否存在可下载、可复现的发布产物；
- 版本是否能与具体字节对应；
- 插件之间是否有名称、目录、`skin id`、`bodyAttr` 或依赖冲突；
- 许可证是否允许使用、托管和再分发；
- 需要由作者维护的内容和需要由宿主维护的内容分别是什么；
- 下游是否能消费当前目录数据。

收录状态必须把“来源存在”“结构通过”“运行可用”分开。推荐使用以下状态语义：

| 状态 | 含义 |
| --- | --- |
| `candidate` | 已发现来源，但产物、许可或身份资料尚不完整 |
| `source-verified` | 来源、版本、作者和许可证已核对 |
| `structure-validated` | 归档结构、清单身份和 SHA-256 已通过 Mojobox 检查 |
| `runtime-verified` | 在指定宿主、加载器、版本和环境下完成运行验证 |
| `blocked` | 存在明确阻塞，例如没有根入口、没有产物或许可不明 |
| `withdrawn` | 来源撤回、产物失效或维护者要求停止分发 |

状态之间不是自动升级关系。静态 Schema 通过不能自动产生运行证据，单次本地运行成功也不能自动产生跨版本兼容承诺。

### 3.4 后续提供面向下游的接口

接口建设排在收录稳定之后。第一阶段只需要让下游能够可靠读取生成的目录文件；后续再提供稳定 API。

接口至少应能表达：

- 插件和整合包的稳定 ID；
- 当前版本和历史版本关系；
- 原始来源和固定 revision；
- 下载 URL 和 SHA-256；
- 作者、许可证和再分发说明；
- 依赖、冲突、平台和宿主要求；
- 静态检查结果与运行证据；
- `candidate`、`validated`、`withdrawn` 等发布状态。

下游接口的目标是提供可靠事实，不把 Mojobox 的内部文件布局泄露成永久协议，也不把某个加载器的私有运行时字段强行变成所有下游都必须实现的字段。

### 3.5 开发面向广泛开发者的动态网站

当前静态网站先验证目录、展示和下载链路。动态网站是后续产品化阶段，面向插件作者、皮肤作者、整合包作者和下游工具开发者。

动态网站可以逐步提供：

- 开发者提交入口；
- 来源和版本信息填写；
- 归档上传和 SHA-256 检查；
- 收录状态跟踪；
- 审核意见和补充材料；
- 版本更新和撤回；
- 许可证与署名信息展示；
- API 文档和下游接入示例。

动态网站仍然只是收录与分发平台。它不能直接执行插件，不能读取用户本机 Profile，也不能在浏览器中绕过宿主启动桌面程序。

## 4. 目录中的对象层次

Mojobox 需要区分四类对象，避免把插件、皮肤包和整合包混成一个概念。

### 4.1 插件记录

插件记录描述一个可被宿主或加载器识别的独立插件。至少包含：

- 稳定 ID；
- 包名和版本；
- Host 或 Client 入口；
- 来源仓库、Release 或 registry 地址；
- 固定 revision 或版本依据；
- artifact URL 和 SHA-256；
- `package.json.dsh` 或其他上游元数据投影；
- 许可证、作者和维护状态。

插件记录不代表 Mojobox 拥有插件代码，也不代表插件已经在所有宿主中可用。

### 4.2 功能整合包

功能整合包是多个功能插件的组合声明，优先使用宿主已经定义的 Feature Pack v1。它可以被宿主市场读取，并在宿主具备相应能力时触发安装。

Mojobox 只接收开发者交付的薄包，默认不从多个插件记录中自行拼装生产包。确需维护者组合时，必须明确记录维护者身份、组合依据、版本锁定方式和责任边界。

### 4.3 皮肤包

皮肤包是一个或多个皮肤插件的组合声明。它可以包含皮肤管理器、主题组件和明确声明的依赖，但不应把皮肤素材、源码覆盖目录或宿主构建树直接塞进薄包。

皮肤包的可用性取决于皮肤加载器、宿主版本和其他皮肤的冲突规则。Mojobox 只能记录这些条件，不能替加载器执行它们。

### 4.4 皮肤 Prompt 资料包

皮肤 Prompt 资料包使用上游 `skin-prompt-package-v1`，包含 `manifest.json`、`prompt.md` 和说明文件，供 AI 阅读、复刻和继续设计。它不是可安装插件，不进入宿主安装索引；Mojobox 只固定来源提交、文件摘要和目录展示。

### 4.5 证据记录

证据记录绑定一个具体版本、具体 artifact、具体宿主或加载器、具体测试套件和测试时间。它描述一次可复核的结果，不是永久兼容声明。

## 5. 收录流水线

所有类型的收录都应逐步经过以下流程：

```text
发现上游来源
    ↓
收集身份、版本、许可证和发布产物
    ↓
核对固定来源与 SHA-256
    ↓
静态检查清单和归档结构
    ↓
记录候选 / 已验证 / 阻塞状态
    ↓
生成目录、报告和下载文件
    ↓
由宿主或下游加载器独立完成运行验证
```

静态阶段不得执行插件、安装依赖、运行生命周期脚本或修改用户环境。运行阶段必须使用隔离环境，并在证据中记录实际版本和限制。

正式发布前至少要能回答：

1. 这是谁维护的？
2. 这个版本来自哪里？
3. 下载的字节是否与记录的摘要一致？
4. 包内声明了哪些插件和版本？
5. Mojobox 实际检查了什么？
6. 哪些内容仍然没有验证？
7. 下游应该如何消费或拒绝它？

## 6. 安装能力边界

功能整合包可以拥有一定程度的安装支持，但这个能力必须依附于宿主：

| 能力 | Mojobox 负责 | 宿主或下游负责 |
| --- | --- | --- |
| 目录查询 | 提供包和版本数据 | 读取目录 |
| 归档下载 | 提供原始文件和摘要 | 下载并核对摘要 |
| 清单检查 | 检查结构和字段 | 可再次检查 |
| 安装计划 | 可提供来源和声明 | 判断本机是否满足条件 |
| 实际安装 | 调用已有接口或提供归档 | 执行安装事务 |
| Profile 修改 | 不负责 | 宿主负责 |
| 快照和回滚 | 不负责 | 宿主负责 |
| 插件运行 | 不负责 | 宿主负责 |
| 皮肤加载与切换 | 不负责 | 皮肤加载器负责 |

因此，“支持安装”只能表述为“为支持该格式的宿主提供安装来源”或“通过宿主已有安装接口支持安装”。不能表述为 Mojobox 自己拥有完整安装器。

## 7. 皮肤包专项边界

皮肤包开发应遵循以下规则：

1. 皮肤作者负责皮肤代码、素材、注册方式和上游发布。
2. 皮肤加载器作者负责发现、加载、切换和运行时兼容。
3. Mojobox 负责记录皮肤包组成、来源、版本、许可证、冲突和归档摘要。
4. Mojobox 可以提供皮肤包下载，但不提供桌面端加载按钮或自定义注入逻辑。
5. 同一 `skin id`、`bodyAttr`、CSS 命名空间或主题注册点出现冲突时，必须记录为限制或阻塞。
6. 源码覆盖宿主目录的项目不能直接伪装成标准插件；必须由上游提供可安装的根插件或明确的适配产物。
7. 缺少许可证、来源或可核验 artifact 的皮肤只能保留为候选资料。

## 8. 公开收录标准

### 插件最低材料

- 稳定包名或插件 ID；
- 版本；
- 可访问的 HTTPS 来源；
- 插件入口或上游包元数据；
- 作者和许可证；
- 可核验的发布产物或明确的未发布状态。

### 整合包最低材料

- 完整 `.dshpack`；
- 根 `pack.json`；
- 至少一个插件引用；
- 精确版本或作者声明的版本范围；
- 来源页面；
- 作者和许可证；
- 最终归档 SHA-256。

### 皮肤包额外材料

- 皮肤类型和加载方式；
- 是否依赖皮肤加载器；
- 是否包含管理器或切换器；
- 已知冲突键和互斥规则；
- 预览图来源；
- 代码与美术素材的许可证边界；
- 宿主版本和加载器版本声明。

材料不完整时可以进入候选区，但不能进入“已验证可用”目录，也不能向下游隐藏缺失信息。

## 9. 发布状态和更新规则

每个稳定 ID 当前可以有一个默认推荐版本，但不能覆盖历史事实。版本变化必须产生新的版本记录和新的摘要。

以下情况必须重新检查：

- artifact 字节变化；
- `pack.json` 变化；
- 插件版本变化；
- 上游固定 revision 变化；
- 许可证或再分发条件变化；
- 依赖、冲突或宿主要求变化。

来源撤回、许可证争议、artifact 不可访问或已知严重冲突时，可以将记录标记为 `withdrawn` 或 `blocked`。撤回不应抹去历史记录，网站需要展示撤回原因和时间。

## 10. 开发阶段与完成标准

### 阶段一：功能整合包收录基础

目标：保持当前 Mojobox 框架可用。

完成标准：

- 能接收薄 Feature Pack v1；
- 能静态检查清单、归档结构和 SHA-256；
- 能生成目录、报告和原始下载；
- 能明确显示“来源未解析”和“宿主未测试”；
- 宿主安装只通过已有接口完成。

### 阶段二：皮肤包收纳

目标：在不开发加载器的前提下收录真实皮肤插件和皮肤包。

完成标准：

- 插件记录可以表达皮肤来源和包元数据；
- 薄皮肤包可以复用现有静态检查链路；
- 目录能够显示皮肤类别、加载器依赖和冲突限制；
- 至少收录一组来源清楚的真实皮肤包；
- 未验证的加载器兼容性不会被显示为已确认。

### 阶段三：真实内容与规范沉淀

目标：用真实包确定稳定边界。

完成标准：

- 至少有功能整合包和皮肤包的真实样本；
- 每类样本都有来源、版本、许可证和摘要；
- 至少有一组正向宿主或加载器运行证据；
- 冲突、撤回和未发布状态有明确表示；
- 收录规则能被陌生开发者理解和执行。

### 阶段四：下游接口

目标：让宿主市场、皮肤加载器和第三方工具稳定消费目录。

完成标准：

- 目录有稳定版本标识；
- 插件、整合包、artifact 和证据关系可查询；
- 下游能根据状态和摘要决定下载、接受或拒绝；
- API 变更有版本和兼容策略；
- 接口不要求下游依赖 Mojobox 内部目录路径。

### 阶段五：动态开发者网站

目标：把人工收录流程逐步变成面向社区的提交和审核流程。

完成标准：

- 开发者可以提交包和来源材料；
- 系统能自动检查格式、摘要和重复版本；
- 维护者可以补充审核意见和状态；
- 页面能展示缺失材料、限制和证据等级；
- 生成目录和 API 仍然来自可审计的数据源；
- 网站不直接执行插件或修改用户桌面端。

## 11. 当前优先级

当前应按以下顺序投入开发：

```text
功能整合包收录与基础安装支持
        ↓
皮肤插件与皮肤整合包收纳
        ↓
真实包验证、冲突记录和规范沉淀
        ↓
下游目录接口
        ↓
动态开发者网站
```

当前皮肤包分支先完成第二阶段的本体接纳结构：收录 Schema、静态目录构建和网站展示。随后再将已有来源整理为正式皮肤包；宿主安装器、皮肤加载器和动态网站仍属于下游或后续任务。

## 12. 关键风险和处理原则

### 上游产物与源码不一致

固定 Git revision 不自动证明 npm tarball 或 Release artifact 与源码完全相同。目录必须分别记录源码来源和最终归档摘要，不得把二者等同。

### 许可证和素材权利不清

代码许可证不一定覆盖人物素材、壁纸、音频和游戏相关标识。许可证不清时可以记录候选来源，但不能默认允许 Mojobox 再分发。

### 皮肤冲突

皮肤可能共享相同注册 ID、DOM 属性、CSS 选择器或主题服务。Mojobox 只记录冲突并向下游暴露，不能在目录层面宣称多个冲突皮肤可以同时启用。

### 静态检查被误读为可用证明

网站和报告必须明确显示检查范围。结构通过只代表文件可被收录，不代表安装成功、运行成功、安全或跨版本兼容。

### 中介平台变成新的安装器

当需求涉及 Profile、快照、回滚、插件执行、桌面注入或加载器状态时，应交给宿主或下游项目。Mojobox 只补充目录事实、归档和接口所需数据。

## 13. 决策原则

后续出现边界争议时，按以下原则判断：

1. 优先保存上游事实，不替上游创造事实。
2. 优先复用已有宿主和加载器能力，不在 Mojobox 复制运行时。
3. 优先收录真实、可追溯的小样本，不为假设场景扩展协议。
4. 把“来源”“结构”“安装”“运行”分成独立状态。
5. 能通过目录数据解决的问题，不新增宿主或网站功能。
6. 需要执行代码或修改用户环境的问题，转交下游组件。
7. 所有发布结论都绑定具体版本、具体字节和具体验证环境。

本文的目标不是让 Mojobox 承担整个 DSH 生态，而是让生态中的已有作者和工具可以通过一个可靠的中间目录互相连接。
